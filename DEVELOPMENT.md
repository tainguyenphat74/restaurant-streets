### Honors pacing: optimistic bounded continuation, not player metrics

The same reproducible fresh run in `src/state/pacing.test.ts` continues from both streets at level 25 to all level 50, then all level 100. It retains actual earned coins and levels; no injected wealth or reset at checkpoints. Choose the next affordable-target candidate by lowest cost / marginal **total** income, including the final upgrade’s street bonus. Wait for every cost and collect all registers at intervals of at most 60 seconds. Only the two previously purchased Riverside managers are used; no global upgrades, boosts, offline periods or human action latency. The policy never upgrades above the current 50/100 target and is not a proof of optimal play. Loops have convergence guards and finite broad bounds.

Cumulative time from fresh: Maple 50 **6,134.04s (102.23m)**; Riverside 50 **7,274.63s (121.24m)**; Maple 100 **705,702.08s (8.17 days)**; Riverside 100 **950,393.26s (11.00 days)**. The unchanged exponential costs produce a very steep level-100 tail: these honors are not evidence that late progression is comfortably paced. Globals/boosts can shorten timing; missed collections/offline-only play can lengthen it. No nerf, timing concealment or fabricated retention/completion metrics; further balancing is outside this slice.

### Simulation-backed pacing assumptions

`npm test -- src/state/pacing.test.ts --reporter=verbose --silent=false` reproduces the simulation. It starts with the real fresh balance, chooses the lowest cost per marginal income for Maple upgrades through level 25, waits for every cost, and collects every at most 60 seconds. Actions have zero human latency; there are no global upgrades, boosts, offline periods or managers before the goal. This is an optimistic active-play policy, **not measured completion/retention or a promise of player timing**.

The simulation reaches all six Maple level-25 restaurants in **1,674.32 seconds (27.91 minutes)** at **3,306,712.5 coins/s**. From that goal, River Grill opens in **3.63 seconds**. Buying its manager before opening Gelato puts Gelato's opening at **56.78 seconds**; both managers are hired by **217.14 seconds (3.62 minutes)**. Continuing lowest marginal payback upgrades to level 25 for both Riverside restaurants takes **1,020.73 seconds (17.01 minutes) after the goal**. Existing global upgrades/boosts can accelerate this; missed collections and offline-only play slow it. The fast first opening deliberately makes the earned unlock immediately useful; the two restaurants' upgrades supply the bounded follow-on progression. No player metrics were fabricated.

- Inspect Git state and this file first; preserve and resume intended interrupted work instead of overwriting it.
- Build small independently useful slices and commit sequentially. Prefer Codex implementation and independent review/testing; if its CLI quota blocks a bounded task, direct implementation with the same tests/review is permitted by the owner's broad authorization. Record actual blockers rather than endlessly retrying.
- Require unit tests, TypeScript/production build, diff checks, relevant desktop/mobile browser interactions and save compatibility checks before publication.
- Push normally to `main` only after checks pass. A main push currently creates a preview: wait for the exact SHA's deployment, promote it if needed, and wait for the resulting production deployment. Never blindly create duplicate deployments.
- Verify source SHA, Ready production state, custom-domain alias and actual live feature interactions before marking a release live. A docs-only push after verification needs no promotion when runtime code is unchanged.
- Failed verification means no release. Record blockers and retain recoverable work. Never discard other work or overwrite player saves to make tests pass.
- Scheduled runs take one coherent release at most. Avoid overlapping writers using `/tmp/restaurant-streets-autodev.lock`. When the queue is complete, audit and fix meaningful regressions rather than adding filler features.
